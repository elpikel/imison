# Decision log

Dated decision log: what, why, what was rejected.

- 2026-11-11: Claude kit set up (copied from ether). Repo is a plain Mix library, not a Phoenix app; web and DB rows in `.claude/project.md` point at the host app and the future `dev/` app.
- 2026-11-11: Design adopted from "Imison: architecture and user stories" (`docs/PROJECT.md`). Name is Imison (`:imison`), matching the repository and the `mix new` skeleton. ADRs 0001–0003 accepted; 0004 (built-in login) and 0005 (no hard Oban dependency) proposed until the open decisions are settled.
- 2026-11-11: Tooling: Styler formatter plugin, Credo `--strict` with the ExSlop plugin.
- 2026-11-11: Work tracking: no issue tracker; plans and tasks live in `.claude/work/<slug>/`; `/implement` needs a feature branch off `main`.
- 2026-11-11: Dashboard design added as static mockups in `docs/design/` (`app.css` + one HTML page per screen). LiveViews reuse its markup and class names. `app.css` moved to `priv/static/app.css`, the shipped asset, and the mockups link to it.
- 2026-11-11: Fonts bundled instead of loaded from Google Fonts, so host apps' dashboards make no third-party requests and pass strict CSP. Instrument Sans (variable, 400–700) and JetBrains Mono (400, 600), latin + latin-ext WOFF2 from Fontsource 5.3.0, in `priv/static/fonts/` with their OFL 1.1 licenses, which the OFL requires when redistributing. Rejected: system font stack (loses the design's look).
- 2026-11-11: Backlog in `docs/STORIES.md`: the design's 36 stories with IDs, build order, dependencies and "done when" lines, plus DEV-01 (test database) and DEV-02 (`dev/` host app) as setup. Replaces the story table in `PROJECT.md` so there is one list.
- 2026-11-11: `mix check` alias runs in the test env: `compile --warnings-as-errors --force`, `deps.unlock --check-unused`, `format --check-formatted` (Styler), `credo --strict` (ExSlop), `test`. It stops at the first failure.
- 2026-11-11: Test database (DEV-01): `mix test` runs the standard alias `ecto.create` + `ecto.migrate` on `imison_test`, never drops it. After editing an unreleased `Imison.Migration` version, reset by hand with `MIX_ENV=test mix ecto.drop`, then `mix test`. Rejected: dropping and recreating on every run; migrating from `test_helper.exs` with `Ecto.Migrator`. Wrapper migrations live in `test/support/postgres/migrations/` (test repo `priv:`), outside the package, one per released version, as a host app does.
- 2026-11-11: `Imison.Migration` added as a stub in DEV-01: `up/1` and `down/1` are no-ops, so the test repo's wrapper migration goes through it now and INS-02 only adds version 1. Rejected: leaving the wrapper migration empty until INS-02 (misses DEV-01's "done when").
- 2026-11-11: `ecto_sql ~> 3.14` and `postgrex ~> 0.22` added as required dependencies now: they were already planned runtime deps in `docs/PROJECT.md`, and the test repo needs them. Rejected: `optional: true` (Imison's migration and schemas always need them, as Oban's do).
- 2026-11-11: Tests cover Imison's behaviour only: no tests of framework behaviour (Ecto's SQL sandbox or migrator) or of no-op stubs. DEV-01 adds no tests of its own: `mix test` going green through the `ecto.create` + `ecto.migrate` alias is the check, and sandbox isolation, test-only compilation and the wrapper migration running were checked once by hand. Real database tests arrive with INS-02, which uses `Imison.DataCase`.
- 2026-11-11: Development host app (DEV-02): `dev/` is a gitignored, local-only Mix project with a path dependency on Imison (user's choice: not pushed to the repo), so the library's `mix.exs` and deps are unchanged and `dev/` can't enter the Hex package. Built by hand: endpoint, router, one controller with sample error routes and an error view; `mix dev` creates and migrates `imison_dev` and starts the server. Errors render as plain text (no `phoenix_html`). Checked by hand, no tests. Rejected: a `dev.exs` script with `only: :dev` deps in the library's `mix.exs` (dev-only code and deps in the repo); a committed `dev/` project; `phx.new` (assets and generators the app doesn't need).
- 2026-11-11: Config validation (INS-05) follows Oban: `Imison.start_link/1` calls `Imison.Config.new/1`, which raises `ArgumentError`, so a bad config fails the host's boot. `Imison.Validation` is hand-written, modelled on `Oban.Validation` with only the types Imison uses. Unknown options are rejected with a "did you mean" hint; duplicate options are rejected; `repo` must export `config/0`, `mailer` `deliver/2`, and `ignore` entries must be exception modules. The config is stored in `Imison.Registry` (started by `Imison.Application`) as Oban does in `Oban.Registry`, and read with `Imison.config/1`. `%Imison.Config{}` holds every documented option with its default; `channels` defaults to `[]` until NOT-01 adds the email channel. Error messages print the given value, as Oban's do. Rejected: `nimble_options` (Oban hand-writes its validator; no new dep); validating only the three options used now; redacting credential values in messages (user's choice to keep Oban's format).
- 2026-11-11: Migrations (INS-02) mirror Oban. `Imison.Migration` is the public module and a behaviour (`up/1`, `down/1`, `migrated_version/1`) that dispatches on the repo's adapter; `Ecto.Adapters.Postgres` → `Imison.Migrations.Postgres` is the only mapping. The applied version is recorded as a comment on `imison_errors`; `up()` migrates to the latest, `up(version: n)` applies only missing versions, `down(version: n)` rolls back to n−1. `V01` creates the six tables with `create_if_not_exists`. A `prefix:` option puts them in another Postgres schema (created when missing), with a matching `prefix` config option, default `"public"`. Ids are explicit `bigserial`, references `bigint` and timestamps `utc_datetime_usec`, so the host repo's migration config can't change them. Status-like values are text (schemas validate them later). Other indexes wait for the stories whose queries need them. Until the first Hex release later stories edit `V01`; afterwards each change is a new version. INS-07 is folded in: Oban's version tracking is its "done when". `.formatter.exs` imports the `ecto` and `ecto_sql` formatter config so the migration DSL has no parentheses. Rejected: Postgres logic directly in `Imison.Migration` without dispatch or prefix; `V01` without version tracking (INS-07 would rewrite it).
- 2026-11-11: Name fixed to Imison, matching the repository: the design doc's spelling with an extra "i" had been adopted earlier the same day and is replaced everywhere (OTP app `:imison`, modules `Imison.*`, tables `imison_`, env vars `IMISON_USER`/`IMISON_PASSWORD`, test DB `imison_test`); earlier entries use the current name. Nothing was released, so no upgrade path is needed. The `.gitignore` pattern `imison-*.tar` is now correct.
- 2026-11-11: Error grouping (ERR-01, with MN-01 folded in): `Imison.Errors.record/2` is the seam the capture worker and `report/3` will call; it takes the config and a map (`kind` as a string, `message`, `stacktrace`, `context`, `release`, `occurred_at`) and writes error, occurrence and hourly count in one `repo.transact`, every write with `prefix`. Increments happen in SQL, so concurrent records from several nodes sum (MN-01). Application frames are modules of the host repo's `otp_app`; rejected: an `otp_app` config option (one more setting). With no application frame the fingerprint uses the first frame, and an empty stack trace hashes the kind alone; rejected: grouping on kind alone whenever no application frame exists (lumps unrelated crashes). The latest message wins, guarded by `occurred_at`: one `ON CONFLICT` statement sets `last_seen_at` with `GREATEST` and `message` with a `CASE` on it, so reordered or concurrent capture can't move `last_seen_at` back; rejected: keeping the first message (stale wording), a plain `set` (an older occurrence would overwrite). Hash input is kind, module, function and arity joined by `"\n"`, built with `Atom.to_string`, so an Elixir upgrade (e.g. `inspect` output) can't change fingerprints. Stored frames keep module, function, arity, file and line, never argument values. Plain structs and `insert!`, no changesets: the input is internal. MN-01's concurrency test commits real rows via `Sandbox.unboxed_run` and deletes them by a unique `kind`, so other tests assert only on their own rows.
- 2026-11-11: Asynchronous capture (CAP-04): `Imison.Capture.capture/2` runs in the caller, looks up `Imison.Capture.Worker` with `Imison.Registry.lookup/2` and casts the event; no instance under the name, or `Imison.Registry` itself not running (the `:imison` app not started or stopped) → `:ok`; the worker's `message_queue_len` at or above the queue limit → the event is dropped and a `:counters` counter (`write_concurrency`) is incremented; it always returns `:ok`. The worker registers with `Imison.Registry.via/3`, the counter and queue limit as its Registry value, as Oban registers role processes, so callers read both without messaging the worker. The event is `Errors.record/2`'s map without `release`; the worker adds `conf.release`. Failures inside the worker are caught (`catch kind, reason`, covering raise, throw and exit), logged with `Logger.error(..., domain: [:imison])` so CAP-01's logger handler can skip them, and the worker keeps going. The queue limit is a worker start option (default 1 000); tests that need a small one start the worker directly with `start_supervised({Imison.Capture.Worker, conf: conf, queue_limit: 2})` instead of through `{Imison, opts}`, because `Config.new/1` rejects unknown options. Tests wait for the worker with `:sys.get_state/1` and fill the queue with `:sys.suspend/1`; that the supervisor restarts a crashed worker is OTP's behaviour and not tested. `.credo.exs` configures `MissedMetadataKeyInLoggerConfig` with `metadata_keys: [:domain]`, since `domain` is an Erlang logger key, not formatter metadata. `Imison.Registry.lookup(name, role \\ nil)` (modelled on `Oban.Registry.lookup/2`, built on the private `key/2`, so the key shape stays inside `Imison.Registry`) returns `{pid, value}` or `nil`, and rescues the `ArgumentError` that `Registry.lookup/2` raises when the registry isn't running, so every caller gets `nil` instead of a crash; `Imison.Registry.config/1` uses it too. That absent-registry path isn't tested: reaching it means stopping the `:imison` application mid-suite, which would break every other test (verified by hand with `mix run --no-start -e 'Imison.Capture.capture(:x, %{})'`). `Imison.Capture.dropped/1` returns 0 when no instance runs under the name (it's a count). The failure-logging test captures with `capture_log([metadata: [:domain]], ...)` and asserts `domain=elixir.imison` (Logger prefixes `:elixir`), so dropping the domain fails it. Rejected: `GenServer.call` (blocks the caller); a public `queue_limit` option (YAGNI until someone needs to tune it); counting drops in the worker (it's the one that's behind); an internal option passed through `{Imison, opts}` for the limit (would need a hole in config validation).
- 2026-11-11: Capture without code changes (CAP-01): `Imison.Capture.Handlers`, a GenServer child after the worker, traps exits, attaches an Erlang `:logger` handler (`Imison.Capture.LoggerHandler`) and telemetry handlers (`Imison.Capture.Telemetry`) in `init` and detaches them in `terminate`, so each instance's handlers go away with it (tests start an instance per test and don't cross-talk). `init` detaches both before attaching: a predecessor killed without `terminate` (`:kill`, a brutal shutdown) leaves its handlers attached, and a strict `:ok = attach(...)` would then fail every restart until the supervisor's restart intensity ran out and took the host down. The logger handler id is the atom `:"Elixir.Imison.Capture.LoggerHandler.<hash>"`, the hash being `:erlang.phash2(name, 2^32)` (`:logger` ids must be atoms; one atom per instance; an atom built from `inspect(name)` hit `system_limit` past 255 characters, failing boot for a long name); the telemetry handler id is `{Imison.Capture.Telemetry, name}`; both carry the name in their config. The logger handler acts only on events with `crash_reason` metadata (set by Elixir's logger translator, verified for GenServer, Task and `spawn` crashes, each logged once): `{exception, stacktrace}` → `:error`, `{{:nocatch, value}, stacktrace}` → `throw`, other reasons → `exit`. Elixir's translator already normalises Erlang errors in `crash_reason`, so a GenServer crashing on `:badarith` arrives as `{%ArithmeticError{}, stacktrace}` and is recorded as `ArithmeticError`; only real exit reasons (`{:stop, reason, state}`, `exit(reason)`) arrive as plain terms and get kind `exit`. It skips domains `:imison` (Imison's own logs), `:cowboy` and `:bandit`, as Sentry's logger handler does: dedup of request crashes works by dropping the web server's log and keeping the Phoenix telemetry report, which carries the request. Telemetry handlers for `[:phoenix, :router_dispatch, :exception]` (context `request`: method, path, query string, params, headers; `Plug.Conn.WrapperError` unwrapped by matching its struct name, so no Plug module is referenced) and `[:oban, :job, :exception]` (context `metadata.job`: worker, queue, args, attempt) are named functions, not closures (telemetry warns about local functions). The Oban handler is attached unconditionally instead of only when `Code.ensure_loaded?(Oban)`: an event nobody emits never fires, no code references Oban (ADR 0005), and the conditional couldn't be tested without Oban as a dep. Handlers run in the crashing process, wrap everything in `try/catch` (a raising `:logger` handler is removed, a raising telemetry handler detached) and log their own failures under `domain: [:imison]`, which the logger handler skips. The "failure + context → event" builder is `Imison.Capture.event/2`, taking `%{kind, reason, stacktrace}` (the shape of the telemetry metadata, so handlers pass it through; `report/3` in CAP-02 will build the same map); `:error` reasons go through `Exception.normalize/3`, kind is the `inspect`ed module, exits use `Exception.format_exit/1`. Context values JSON can't encode (structs including `Plug.Upload`, tuples, pids, invalid UTF-8, improper lists) are `inspect`ed and keys stringified, so the jsonb insert can't fail and an upload request keeps its event. `ignore` is applied in the worker by comparing the event's kind with `inspect(module)`, so handlers stay build-and-cast only. `telemetry ~> 1.3` became a runtime dep (already locked through Ecto); `plug ~> 1.16` is test-only, so tests emit the Phoenix event with a real `%Plug.Conn{}` from `Plug.Test.conn/3`. Logger metadata kept on crashes: `pid` and `registered_name` (`initial_call` isn't set by the translator). Tests crash real processes (GenServer, Task), wait deterministically (monitor the crashed process: its crash log, and so the handler's cast, happens before it exits; then `:sys.get_state/1` on the worker), assert on a unique message, wrap crashes in `capture_log` and are `async: false`, as is every test module that starts an instance (`test/imison_test.exs` included): ExUnit runs async modules before sync ones, so no instance's global handlers are attached while async tests crash processes, which would cast their crashes to a worker without sandbox access; the shared builders (`start_imison/1`, `wait_for_worker/1`, `raised/1`, `recorded/1`, `unique_message/0`) live in `Imison.Test.CaptureHelpers` (`test/support/capture_helpers.ex`); web-server and Imison crash logs are emitted with `:logger.error/2` and a metadata map (Credo's `MissedMetadataKeyInLoggerConfig` flags `crash_reason` in `Logger.error`). Rejected: capturing every `Logger.error` (noise; `report/3` covers handled errors); deduplicating request crashes by matching conn metadata (fragile); one global logger handler shared by all instances (AC8 needs per-instance detach); applying `ignore` in the handlers (more work in the host's process).
- 2026-11-11: Filter sensitive data (CAP-03): `Imison.Capture.Filter.filter/2` replaces the value of every atom or string key whose downcased name contains one of the `filter` words (downcased) with `"[FILTERED]"`, walking maps, struct fields (kept as the same struct, so an `inspect`ed struct shows `[FILTERED]`), lists (improper tails too), `{key, value}` pairs and other tuples at any depth. Substring and case-insensitive matching, as Phoenix's `filter_parameters` does, so `password_confirmation` and `X-Api-Token` are caught. A custom `filter` replaces the default list (no merging). Filtering runs in the worker, and the JSON-safe conversion moved from `Imison.Capture.event/2` into the worker after it: handlers now cast the raw context, the worker filters, then `inspect`s what JSON can't encode, so a filtered value is never `inspect`ed and every path (logger, Phoenix, Oban, CAP-02's `report/3`) is filtered in one place. The request context no longer stores `query_string`: its values are already in `params`, filtered (the CAP-01 telemetry test's `query_string` assertion was removed). AC3 (metadata at any depth) is tested through a failing Oban job's args, since `report/3` doesn't exist yet. Imison's failure logs (handlers and worker) go through `Imison.Capture.FailureLog.error/2`: argument lists in the stack trace are reduced to arities and a `FunctionClauseError` banner drops its `args`, because `Exception.format/3` printed the top frame's arguments (a whole conn with its cookies, or an unfiltered event); the domain stays `[:imison]`. Tested by emitting a Phoenix exception event without `kind`/`reason`/`stacktrace` (a `FunctionClauseError` in the handler) and refuting the cookie and param values in the log. Exception messages are still logged and stored as they are (`imison_errors.message`), so an exception whose message embeds a value (`KeyError`, `MatchError`) could still show it, as with Sentry; filtering is by key only. Map keys aren't walked, so a secret inside a composite key (e.g. a `MapSet` element) survives; no capture path carries one today. Rejected: exact key matching (misses `password_confirmation`, `x-api-token`); filtering in the handlers (cost in the crashing process); filtering after the JSON-safe conversion (a filtered value inside a struct or tuple would already be `inspect`ed into a string); keeping the query string and filtering it as a string (duplicates `params`); dropping exception messages from failure logs (loses the reason, e.g. a database error).
- 2026-11-11: Report rescued exceptions (CAP-02): `Imison.report(exception, stacktrace, metadata \\ %{})` lives in `lib/imison.ex` and builds the event with the handlers' builder, `Imison.Capture.event/2`, from `%{kind: :error, reason: exception, stacktrace: stacktrace}`, so kind, message and `occurred_at` come from one place and a non-exception value (an Erlang error term such as `:badarith`) is normalized by `Exception.normalize/3` like any `:error` reason. Metadata (a map, or a keyword list converted with `Map.new/1`) goes under the context's `metadata` key, the key the Oban handler already uses for its job, then `Imison.Capture.capture(Imison, event)` casts it; `ignore`, filtering and the JSON-safe conversion happen in the worker, so a token nested in report metadata is stored as `[FILTERED]` like any other context. It reports only to the default instance named `Imison` (documented in its `@doc` and the README). It always returns `:ok` and never raises: with no instance running `capture/2` already does nothing, and anything raised while building the event (e.g. metadata that is neither a map nor a keyword list) is caught (`catch kind, reason`) and logged through `Imison.Capture.FailureLog` under `domain: [:imison]`, as the handlers do; the public head has no guards, so a wrong argument type can't raise a `FunctionClauseError` in the caller. Tests (`test/imison/report_test.exs`, `async: false`) start the instance under the name `Imison` through `start_imison(name: Imison)` (`Imison.Test.CaptureHelpers.start_imison/1` now takes an optional `name`, default a fresh ref) and report from a real `rescue` with `__STACKTRACE__`. Rejected: a synchronous report that returns the error or the recorded occurrence (would block the caller on the database, against CAP-04); `report/4` or a `name:` option for custom-named instances (deferred until someone runs one and asks); merging metadata into the top level of the context (would collide with `request` and the logger's keys).
- 2026-11-11: Capture off in tests (INS-06): with `enabled: false`, `Imison.init/1` starts neither `Imison.Capture.Worker` nor `Imison.Capture.Handlers` (an empty child list); the supervisor still starts and registers its config, so `Imison.config/1` works. No handler is attached, and `report/3` still returns `:ok`: `Imison.Capture.capture/2` finds no worker and does nothing (CAP-04), so no `enabled` check was added to the capture path. The README shows `config :my_app, Imison, enabled: false` in `config/test.exs`. Tests (`test/imison/capture_off_test.exs`, `async: false`) start the instance through `{Imison, opts}` with `enabled: false`, assert no logger or telemetry handler carries its name, and in each "nothing recorded" test first assert no `Imison.Capture.Worker` is registered for the instance (so the test fails if capture were running, since recording is an async cast) and then that nothing is recorded, with no sleeps. The shared `attached_handlers/1` and `wait_for_exit/1` live in `Imison.Test.CaptureHelpers`. Rejected: keeping the handlers and checking `enabled` in each of them or in `capture/2` (work in the host's process for nothing, and a config lookup per event); not starting the supervisor at all (`Imison.config/1` would raise, failing AC3).
