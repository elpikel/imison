# Architecture

Imison is a plain Mix library (OTP app `:imison`) that runs inside a host Phoenix app. This doc describes what is built; the full design, stories and open decisions are in [`docs/PROJECT.md`](docs/PROJECT.md).

## What exists

The `Imison` supervisor (`lib/imison.ex`), which a host starts with `{Imison, opts}` in its supervision tree; `child_spec/1` uses the `name` option (default `Imison`) as the id. `start_link/1` builds an `Imison.Config` struct (`lib/imison/config.ex`) holding every documented option with its default; `Config.new/1` raises `ArgumentError` on a missing, unknown, duplicate or wrongly typed option, so a bad config fails the host's boot. Type checks are in `Imison.Validation` (`lib/imison/validation.ex`, internal), modelled on `Oban.Validation`. The supervisor registers in `Imison.Registry` (`lib/imison/registry.ex`, a unique-key `Registry` started by `Imison.Application`) with the config as its value; `Imison.config/1` reads it back by name. The supervisor's children are the notifications' `Task.Supervisor`, the capture worker and, after it, the capture handlers; with `enabled: false` (default `true`) it starts none of them, so no handler is attached and `Imison.Capture.capture/2` finds no worker and does nothing, while the supervisor still runs and registers its config.

Versioned migrations, modelled on Oban's. `Imison.Migration` (`lib/imison/migration.ex`) is the public module and a behaviour (`up/1`, `down/1`, `migrated_version/1`); it dispatches on the repo's adapter to `Imison.Migrations.Postgres` (`lib/imison/migrations/postgres.ex`), the only implementation. That module records the applied version as a comment on `imison_errors`, so `up/1` applies only missing versions (default: the latest) and `down/1` rolls back down to and including the given one. Each version is its own module: `Imison.Migrations.Postgres.V01` creates the six tables. The `prefix:` option puts them in another Postgres schema; the `prefix` config option (default `"public"`) names that schema for Imison's queries.

Error grouping. `Imison.Errors.record/2` (`lib/imison/errors.ex`, internal) takes the config and one occurrence (kind, message, stack trace, context, release, `occurred_at`) and writes it in one `repo.transact`: it upserts the error on `fingerprint`, incrementing `occurrence_count` in SQL, moving `last_seen_at` only forward and taking the message of the newest occurrence; inserts the occurrence; and upserts the hourly count. Every write uses the configured `prefix`. The capture worker calls it, for handler captures and `report/3` alike. `Imison.Errors.Frame.from_stacktrace/2` reads the stack trace once into frames, given the host repo's `otp_app`; argument values are never stored, only their arity. It also decides, once, whether each frame is an application frame (`application?`: the module's application, from `:application.get_application/1`, is the repo's `otp_app`); the fingerprint and the stored frame both read that field. Each stored frame (`imison_occurrences.stacktrace`) keeps module, function, arity, file, line and `application` (`true`/`false`). `Imison.Errors.Fingerprint` hashes (SHA-256) the kind with the first application frame's module, function and arity, and with none it falls back to the first frame. That frame is also the error's location, `Mod.fun/arity (file:line)`. The Ecto schemas `Imison.Errors.Error`, `Occurrence` and `HourlyCount` map the V01 tables; `Error.statuses/0` lists the status values. The returned error carries two virtual flags about this call, both decided by the database: `created` (this upsert inserted the row: the returned `inserted_at` equals `updated_at`, since every conflict update moves `updated_at` strictly forward) and `reopened` (this upsert flipped it from `resolved`, ERR-09).

Listing errors (ERR-02). `Imison.Errors.list(conf, status: status, search: text)` returns the errors in one status, most recently seen first (`last_seen_at` desc, then `id` desc), at most the 100 most recent; `Imison.Errors.count_by_status(conf, search: text)` returns `%{unresolved: n, resolved: n, ignored: n}` from one grouped query, zero for a status without errors. Both read with the configured `prefix`. A search (trimmed; blank means none) is a case-insensitive `ILIKE '%text%'` on kind, message or location, with `\`, `%` and `_` escaped so they match literally. The `(status, last_seen_at)` index on `imison_errors` serves the list.

Heat strip (ERR-03). `Imison.Errors.hourly_counts(conf, error_ids, now)` reads `imison_hourly_counts` for the given errors and the 24 hours ending with the hour of `now` (the oldest being 23 hours before it) in one query with the configured `prefix`, served by the unique `(error_id, hour)` index, and returns `%{error_id => [24 counts]}`, oldest hour first, with zeros for hours without a row and for errors without any; counts in earlier hours are left out. The caller passes `now`, so the window is fixed by the caller's clock.

Status changes (ERR-08). `Imison.Errors.set_status(conf, ids, status)` sets the status of the given errors in one `update_all` on `imison_errors` with the configured `prefix`, and returns `{:ok, count}`. The status is one of `Error.statuses/0`, as an atom or its text; anything else returns `{:error, :invalid_status}` before any query. Ids are read like `get/2` reads its id (integers or whole-number strings in the `bigint` range; anything else is skipped), through one private `error_id/1` both share. `updated_at` moves to `GREATEST(now, updated_at + interval '1 microsecond')`, the same `dynamic` (`updated_at_moved_forward/1`) the regression upsert sets `updated_at` and `regressed_at` with, so it never moves backwards and `record/2`'s `reopened` (regressed_at equal to updated_at) stays exact after a manual change. `regressed_at` is left as it is. When rows changed and `pubsub` is set, it broadcasts `{:imison, :status_changed, error_ids}` (the changed ids, from the update's `select`) through `Broadcast.status_changed/2`; a broadcast that returns an error or raises is logged by `FailureLog` as "Imison failed to broadcast a status change" and the change stands.

Asynchronous capture. `Imison.Capture` (`lib/imison/capture.ex`, internal) is what capture handlers call: `capture/2` takes the instance name and an event (the map `Errors.record/2` takes, without `release`) and runs in the caller. It looks the worker up with `Imison.Registry.lookup/2`, which returns `nil` when nothing is registered or the registry itself isn't running; with no instance under that name it does nothing, with the worker's mailbox at or above its queue limit it drops the event and increments a `:counters` counter, otherwise it casts the event. It always returns `:ok` and never blocks on the worker. `dropped/1` reads the counter (0 when no instance runs under the name). `Imison.Capture.Worker` (`lib/imison/capture/worker.ex`, internal) is a GenServer started by the `Imison` supervisor; it registers with `Imison.Registry.via/3` under the `Imison.Capture.Worker` role, with `%{dropped: counter, queue_limit: limit}` as its Registry value. The queue limit is a start option (default 1 000), not a config option. The worker filters the event's context, makes it JSON-safe, sets the context's `runtime` to `%{"node" => Atom.to_string(node())}` (the node that caught the error; set last, so a caller's own `runtime` key is replaced), adds the configured `release` and calls `Errors.record/2`; anything raised, thrown or exited is logged by `Imison.Capture.FailureLog` under `domain: [:imison]` (so the logger handler skips Imison's own failures) and the worker carries on with the next event. Before recording, the worker drops events whose kind is a module listed in the `ignore` option. After a successful record, when the `pubsub` option names the host's `Phoenix.PubSub`, the worker broadcasts `{:imison, :recorded, error_id}` through `Imison.Errors.Broadcast` (`lib/imison/errors/broadcast.ex`, internal), which owns the topic (`"imison:" <> inspect(name)`, one per instance) and is also what the dashboard subscribes with; a broadcast that returns an error or raises (e.g. no PubSub running under that name) is logged by `FailureLog` as "Imison failed to broadcast a recorded error" and the error stays recorded. Then the worker hands the error to `Imison.Notifications.Notifier.recorded/2`, which returns at once (see Notifications).

Notifications (NOT-01, MN-02, NOT-02, NOT-03). `Imison.Notifications.Notifier` (`lib/imison/notifications/notifier.ex`, internal) owns the instance's `Task.Supervisor` (its `child_spec/1`, registered with `Imison.Registry` under the role `Imison.Notifications.TaskSupervisor`, started before the worker). `triggers/1` decides what a recorded error notifies from the flags `Errors.record/2` set on it: `[:new]` when `created` (this call inserted the error), `[:regression]` when `reopened` (this call flipped it from `resolved`), otherwise `[]`, so an ignored or unresolved error that happens again notifies nothing. Both flags come from the one upsert's returned row, so under concurrent capture on any number of nodes exactly one call sees each, and each event is notified once without node-local state. `recorded/2` starts one task per trigger under that supervisor, so a slow or stalled mailer never holds up the worker, and anything raised starting it is logged. The task calls `Imison.Notifications.notify(conf, error, trigger)` (`lib/imison/notifications.ex`, internal) and logs whatever escapes it. `notify/3` checks the trigger's rule (`rule_enabled?/2`: the `imison_rules` row's `enabled`, or, with no row, enabled for `new` and `regression` only), builds one `Imison.Notifications.Message` (public struct: trigger, error id, kind, message, location, occurrence count, first and last seen, `regressed_at` (when it last came back, nil if never), and `url`, the error's detail page under the `dashboard_url` option built with `Imison.Web.Paths.error/2`, nil without it) and, for each module in the `channels` option, takes the enabled `imison_channels` row of the module's `type/0` whose `config` passes the module's `validate_config/1`, calls `module.deliver(message, row.config, conf)` and inserts an `imison_deliveries` row (`channel_id`, `error_id`, `trigger`, `status` `sent` or `failed`, `sent_at`). A channel that returns `{:error, reason}` or raises is logged by `FailureLog` ("Imison failed to deliver a notification through <module>") and its delivery is `failed`; the other channels still run. `put_channel/3` and `put_rule/3` upsert a channel's settings on `type` and a rule on `trigger`. For the Notifications screen (NOT-03): `channel_setting/2` reads a channel's stored row by type; `put_channel_and_rules/3` (instance config, channel module, `%{config:, rules: %{trigger => enabled}}`) checks the config with the module's `validate_config/1`, returning `{:error, {:invalid_config, reasons}}` without writing, else upserts the channel, enabled, and every rule in one `repo.transact`; `send_test/3` (instance config, channel module, unsaved config) validates the same way, then calls the module's `deliver/3` synchronously in the caller with `Message.test/0` (trigger `:test`, every error field nil) through the same rescue-and-log path as `notify/3` (a returned error or anything raised, thrown or exited is logged by `FailureLog` and returned as `{:error, reason}`), and records no delivery. Schemas: `ChannelSetting` (`imison_channels`), `Rule` (`imison_rules`; `Rule.triggers/0`) and `Delivery` (`imison_deliveries`; `Delivery.status/1` maps a channel's result to `sent` or `failed`). `Imison.Notifications.Channel` (public) is the behaviour: `type/0`, `validate_config/1` and `deliver/3` (message, the channel's stored settings, the instance config). `Imison.Notifications.Channels.Email` (`lib/imison/notifications/channels/email.ex`), defined only when `Swoosh.Email` is loaded, needs `%{"recipients" => [address, ...]}` (non-empty, each a string matching `local@domain`; `validate_config/1` returns one `recipients: "<address> is not an email address"` per invalid address) and builds a plain-text `Swoosh.Email` from `from` to the recipients, subject `[Imison] <headline>: <kind> in <location>` (`<kind>` alone without a location), the headline `New error` for `:new` and `Came back` for `:regression`; the body opens with `<headline>: <kind>`, for a regression followed by "This error was resolved and happened again at <regressed_at>." ("...happened again." without the time when `regressed_at` is nil), then the part both triggers share: message, location, occurrence count, first seen (times through `Imison.Web.Format.utc_time/1`) and the link, delivered with `mailer.deliver(email, [])`; a `:test` message is subject `[Imison] Test email` with a short body saying delivery works; without `mailer` or `from` it returns `{:error, :mailer_not_configured}`. The `channels` default is `[Imison.Notifications.Channels.Email]` when Swoosh is compiled, else `[]`; `Config.validate/1` refuses a channel module that doesn't export `type/0`, `validate_config/1` and `deliver/3`.

Capture handlers. `Imison.Capture.event/2` builds an event from a failure (`%{kind: :error | :exit | :throw, reason: _, stacktrace: _}`, the shape Phoenix and Oban telemetry metadata already has) and a context map: `:error` reasons are normalized to an exception, whose module (`inspect`ed) is the kind and `Exception.message/1` the message; throws get kind `"throw"` and the `inspect`ed value; exits get kind `"exit"` and `Exception.format_exit/1`. The context is passed through as built; `occurred_at` is `DateTime.utc_now()`. `Imison.report/3` reuses it. `Imison.Capture.Handlers` (`lib/imison/capture/handlers.ex`, internal) is a GenServer child of the `Imison` supervisor, after the worker; it traps exits, attaches both handlers in `init` (detaching any left attached by a predecessor killed without `terminate` first) and detaches them in `terminate`, so stopping an instance removes its handlers. `Imison.Capture.LoggerHandler` (`lib/imison/capture/logger_handler.ex`) is an Erlang `:logger` handler, one per instance (its id is an atom built from a hash of the instance name, so any name fits; its config holds the name). It acts only on log events whose metadata has `crash_reason` (set by Elixir's logger translator for crashed GenServers, Tasks and spawned processes): `{exception, stacktrace}` → `:error`, `{{:nocatch, value}, stacktrace}` → `:throw`, anything else → `:exit` (the translator has already turned Erlang errors such as `:badarith` into exceptions, so only real exit reasons get here). It skips events whose `domain` contains `:imison` (Imison's own logs), `:cowboy` or `:bandit` (request crashes the Phoenix handler already reports). The context is `metadata` with the crashed process's `pid` and `registered_name`. `Imison.Capture.Telemetry` (`lib/imison/capture/telemetry.ex`) attaches one telemetry handler per instance (id `{Imison.Capture.Telemetry, name}`, a named function, not a closure) to `[:phoenix, :router_dispatch, :exception]` (context `request`: method, path, params, headers from `conn`; a `Plug.Conn.WrapperError` reason is unwrapped to the failure it wraps) and `[:oban, :job, :exception]` (context `metadata.job`: worker, queue, args, attempt). Both are attached unconditionally and reference no Phoenix, Plug or Oban module, so a host without them is unaffected. Handlers run in the crashing process; each wraps its work in `try/catch` (a raising logger or telemetry handler is removed) and logs its own failures through `Imison.Capture.FailureLog`.

Filtering. `Imison.Capture.Filter` (`lib/imison/capture/filter.ex`, internal) walks the context (maps, struct fields, keyword and other lists, tuples, at any depth) and replaces the value of every atom or string key whose downcased name contains one of the `filter` option's words (downcased) with `"[FILTERED]"`, as Phoenix's `filter_parameters` matches: with the default words `password_confirmation` and `X-Api-Token` are filtered. A custom `filter` replaces the default list. The worker filters first, then converts what JSON can't encode (structs, tuples, pids, invalid UTF-8, improper lists are `inspect`ed, map keys become strings), so a filtered value is never `inspect`ed and the jsonb insert can't fail; every capture path (logger, Phoenix, Oban, `report/3`) goes through it. The request context holds no query string: its values are already in `params`, where they are filtered.

Reporting rescued exceptions. `Imison.report/3` (`lib/imison.ex`, public) is the manual capture path: it builds the event with `Imison.Capture.event/2` from `%{kind: :error, reason: exception, stacktrace: stacktrace}` (so a non-exception value, such as an Erlang error term, is normalized by `Exception.normalize/3` like any `:error` reason) and the context `%{metadata: metadata}` (a keyword list is converted to a map), then calls `Imison.Capture.capture/2` with the name `Imison`. It reports only to the default instance; instances with a custom `name` can't be reached from it yet. It runs in the caller, always returns `:ok` and wraps its work in `try/catch`, logging its own failures (such as metadata that is neither a map nor a keyword list) through `Imison.Capture.FailureLog`; `ignore`, filtering and the JSON-safe conversion happen in the worker, as for captured crashes.

Failure logs. `Imison.Capture.FailureLog.error/2` (`lib/imison/capture/failure_log.ex`, internal) logs a failure inside Imison (handlers, worker and notification delivery) with `Logger.error` under `domain: [:imison]`: the stack trace's argument lists are reduced to arities and a `FunctionClauseError` banner leaves out its arguments, so a failing handler never prints a conn, its cookies or an event into the host's logs.

Imison's own tests run against Postgres. `test/support/` (compiled only in `:test`) holds `Imison.Test.Mailer` (a Swoosh mailer on `Swoosh.Adapters.Test`, configured in `config/test.exs`; delivery runs in a task, so tests that expect an email call `Swoosh.TestAssertions.set_swoosh_global/1` and are `async: false`), `Imison.Test.CaptureHelpers` (`wait_for_recording/1` waits for the worker, `wait_for_worker/1` also for the notification tasks it started), `Imison.Test.Repo`, configured in `config/test.exs` with the SQL sandbox; `Imison.DataCase`, which checks out a sandbox connection per test; and a wrapper migration in `test/support/postgres/migrations/` that calls `Imison.Migration`, as a host app's migration does. `mix test` creates and migrates the `imison_test` database. `test/support/web/` holds a test host: `Imison.Test.Endpoint` (cookie session, LiveView socket at `/live`), `Imison.Test.Router` (a `:browser` pipeline with `protect_from_forgery`, the dashboard mounted at `/errors` and `/admin/errors` for the instance `Imison.Test.Dashboard`), `Imison.Test.ErrorHTML` and `Imison.ConnCase` (which, like `DataCase`, checks out a sandbox connection per test, shared with the LiveViews the test starts); `test_helper.exs` starts the endpoint and its PubSub (`Imison.Test.PubSub`, which live-list tests also pass as the instance's `pubsub`), configured in `config/test.exs` (with `JSON` as Phoenix's JSON library).

Dashboard mounting (INS-03), modelled on Oban Web. `Imison.Web.Router` (`lib/imison/web/router.ex`) defines the `imison_dashboard(path, opts)` macro, which a host calls inside a scope piped through its `:browser` pipeline. It expands to `scope path, alias: false, as: false` (so the host scope's alias doesn't prefix Imison's modules) holding `get "/assets/:digest/*asset"` to `Imison.Web.Assets`, the login routes (below) and a `live_session` named by `as` (default `:imison_dashboard`) with root layout `{Imison.Web.Layouts, :root}`, `on_mount: {Imison.Web.Auth, :require_sign_in}` and the session `%{"imison_name" => name, "dashboard_path" => full_path}` (`full_path` from `Phoenix.Router.scoped_path/2`, so outer scopes count), with `live "/", Imison.Web.ErrorsLive, :index` `live "/errors/:id", Imison.Web.ErrorLive, :show` and `live "/notifications", Imison.Web.NotificationsLive, :index` (all named by `as`, so the sign-in `on_mount` covers every page). Options are checked with `Keyword.validate!/2` (`imison_name`, default `Imison`; `as`); aliases in a literal option list are expanded in the caller. `Imison.Web.Assets` (`lib/imison/web/assets.ex`) is a plug that reads, at compile time, `priv/static/app.css`, the WOFF2 fonts in `priv/static/fonts/` and one script (`phoenix.min.js` and `phoenix_live_view.min.js` from those packages' `priv/static`, then `priv/static/imison.js`, which connects a `LiveView.LiveSocket` at `/live` with the page's CSRF token). URLs are `<dashboard path>/assets/<digest>/app.css`, `…/app.js` and `…/fonts/<file>`, the digest being an MD5 of every asset, so the stylesheet's relative `url("fonts/…")` resolves unchanged and every URL changes when any asset does; responses carry `cache-control: public, max-age=31536000, immutable`, an unknown digest or file is a 404, and the plug skips Plug's cross-origin JavaScript check (the script is public; Phoenix LiveDashboard does the same). `Assets.path/2` builds the stylesheet and script URLs. `Imison.Web.Layouts` (`lib/imison/web/layouts.ex`) has `root/1` (document head: CSRF meta tag, title, stylesheet, deferred script) and `app/1` (the `docs/design/` top bar with brand, nav (Errors and Notifications, the `current` attribute, default `:errors`, marking its link `aria-current="page"`) and the Sign out button, then `main.page`, headed by the `info` flash as `p.flash.flash--info[role=status]` and the `error` flash as `p.flash.flash--error[role=alert]`, from its `flash` attribute). `Imison.Web.ErrorsLive` (`lib/imison/web/live/errors_live.ex`) reads `Imison.config(imison_name)` in `mount` (raising when no instance runs under that name) and renders the `errors.html` page: `handle_params` reads `status` (default `unresolved`; an unknown value falls back to it) and `q` from the URL and loads the list and the tab counts, both filtered by the search. The tabs are `<.link patch>` links that keep the search; the search box is a form whose `phx-change` (debounced 300 ms) `push_patch`es `?status=…&q=…`, leaving out the default status and a blank search, so the URL always holds the choice. Each row shows the kind (a `<.link navigate>` to the error's detail page, `Paths.error/2`), message, location, occurrence count (with thousands separators, `Imison.Web.Format.with_thousands_separators/1`, shared with the detail page) and a relative last seen (`just now`, `N min ago`, `N h ago`, `N d ago`), plus the "Back again" flag when `regressed_at` is set and the error is unresolved, and a 24-hour heat strip under the "Last 24 hours" column: `handle_params` takes one `DateTime.utc_now()` for both the relative times and `Errors.hourly_counts/3` over the listed errors, and each row (`id="error-<id>"`) gets the design's `div.heat.error-row__heat` with `role="img"`, an `aria-label` of "N events in the last 24 hours" (the strip's total, with thousands separators; "1 event" in the singular) and 24 `<i>` cells. A cell with no events has no `data-l`; otherwise its level is `ceil(4 × count / busiest)`, `busiest` being the row's own highest hourly count, so a count up to a quarter of the busiest hour is level 1, up to a half 2, up to three quarters 3 and above that 4 (the busiest hour is always 4); the foot says how many errors are shown, or "The 100 most recently seen of N errors" when the list is cut. With no rows it shows the design's empty state: for a search, "No matching errors" with a Clear search link; for Unresolved, the mockup's text with a Show resolved errors link; for Resolved and Ignored, "No resolved/ignored errors". Live updates (ERR-04): when connected and the instance's `pubsub` is set, `mount` subscribes with `Broadcast.subscribe/1` and the top bar (`Layouts.app/1`'s `live` attribute) shows the design's `span.live` indicator; the first (disconnected) render and an instance without `pubsub` show none. Each `{:imison, :recorded, _}` message reloads the current tab, search, counts and heat strips through the same `load_list/1` as `handle_params`, throttled to one reload a second: the first message after a quiet second reloads at once and opens a one-second hold (`Process.send_after(self(), :live_reload_hold_over, 1_000)`); messages during the hold only mark a reload pending, done when the hold ends (which opens a new hold), so a burst costs at most one reload per second and the last error of a burst is never lost. Each `{:imison, :status_changed, _}` message (ERR-08) reloads the list the same way, through the same throttle. Selection with bulk actions (ERR-08): each row starts with the design's `input.checkbox.error-row__check` (`aria-label` "Select <kind>", `phx-click="toggle_selection"` with `phx-value-id`) and the list head with a "Select all" checkbox (`phx-click="toggle_all"`: selects every listed row, or clears the selection when all are selected). The selection is a server-side `MapSet` of error ids: an id that isn't a listed row is ignored, `handle_params` (tab change, search) clears it, and every reload keeps only the ids still listed. While rows are selected the design's `div.bulkbar` sits above the list head with "N selected" and one `btn btn--sm` per status change that moves the rows off the current tab (Unresolved: Resolve, Ignore; Resolved: Mark unresolved, Ignore; Ignored: Mark unresolved, Resolve); with none selected it is not rendered. Each button sends `set_status` with `phx-value-status`; the LiveView passes the selection and the raw status to `Errors.set_status/3`, then clears the selection and reloads rows and counts. An unknown status changes nothing. The host's endpoint supplies the LiveView socket at `/live`, the session and PubSub.

Error detail (ERR-05). `Imison.Web.ErrorLive` (`lib/imison/web/live/error_live.ex`) serves `<path>/errors/<id>` and renders `docs/design/error-detail.html`. `mount` loads the error with `Errors.get/2`, which takes the id as given in the URL and returns `nil` for anything that isn't a whole number in the `bigint` range (`"abc"`, `"12abc"`, `"99999999999999999999"`) as well as for an unknown id, without raising; then `push_navigate`s to the list with the `error` flash "That error doesn't exist. It may have been deleted.". Otherwise it loads the error's latest occurrence with `Errors.latest_occurrence/2` (by `occurred_at` desc, then `id` desc, with `prefix`). The page has a Back to errors link; `header.error-head` with the kind, message, a status flag (`flag--unresolved`, `flag--resolved`, `flag--off` for ignored) and the location (`code.error-head__location`, left out when none); the rail (`aside.rail`) with Events (thousands separators), First seen and Last seen as absolute UTC times (`11 Nov 2026, 14:32:07 UTC`, `Format.utc_time/1`). Below the head come the latest occurrence's panels, each left out when it has nothing to show: Stack trace (one `details.frame` per stored frame, `span.frame__fn` `Module.function/arity` and `span.frame__loc` `file:line`, the file alone without a line and no location without a file; frames stored with `"application" => true` are `frame--app` and open, every other frame, including frames stored before ERR-06 without the key, is a muted `frame--dep`; the marking is read from the stored frame, never recomputed, so it survives deploys that rename modules; the panel head shows the design's "The teal edge marks frames in your code" when any frame is an application frame), then Request (Method and path, Params, Headers), Logger metadata (one row per key, sorted) and Runtime (Node from `context.runtime.node`, Release from the occurrence) as the design's `dl.kv` lists. Values are text: strings as they are, anything else (maps, lists, numbers) through `inspect/2` without truncation, all escaped by HEEx, never raw HTML. Status changes (ERR-08): the rail's first block is the design's `div.btn-row`, Resolve (`btn btn--primary`) and Ignore (`btn`) for an unresolved error, Mark unresolved for a resolved or ignored one; each sends `set_status` with `phx-value-status`, and the page calls `Errors.set_status/3` for its error, then re-reads it with `get/2`, so the status flag and buttons follow (an unknown status changes nothing; an error gone meanwhile sends the developer back to the list as on mount). Stepping through occurrences (ERR-07), the heat strips, notifications and fingerprint rail blocks are not built yet.

Notifications screen (NOT-03). `Imison.Web.NotificationsLive` (`lib/imison/web/live/notifications_live.ex`) serves `<path>/notifications` (`Paths.notifications/1`) and renders the Email panel of `docs/design/notifications.html`; the "keeps happening" and "daily summary" rules and the planned Slack, Webhook and Telegram panels are left out. `mount` finds `Imison.Notifications.Channels.Email` in the instance's `channels` (by module, so the screen compiles and renders without Swoosh) and, when it's missing, shows an `.empty` state saying email isn't available and how to enable it, with no form. Otherwise it loads the stored channel (`channel_setting/2`: its recipients joined with ", " and an On/Off flag) and each shown rule's `rule_enabled?/2`. The head's hint is "Sends with <mailer> as <from>" or how to set them. One form (`#email-settings`) holds the "Send to" textarea and a switch per rule (a hidden `false` before each checkbox); `phx-change` keeps the typed recipients and switches in assigns, so "Send test email" (`phx-click`) uses the form's current recipients. Recipients are split on commas and new lines, trimmed, blanks dropped and repeats removed in the LiveView. Save calls `put_channel_and_rules/3` and flashes "Email settings saved."; send calls `send_test/3` and flashes "Test email sent to a@…, b@…." or "Couldn't send the test email: <reason>" (an exception's message, otherwise `inspect/1`). Invalid recipients from either action are listed under the field (`#recipients-errors`) and nothing is stored or sent.

Dashboard credentials (AUTH-01). `Imison.Web.Auth.valid_credentials?/3` (`lib/imison/web/auth.ex`, internal) takes the instance's `%Imison.Config{}` and a submitted username and password and returns a boolean: both fields are compared with `Plug.Crypto.secure_compare/2` and both comparisons always run (no short-circuit), so timing doesn't reveal which field was wrong; non-binary input (such as `nil`) is refused. The credentials come only from the `username` and `password` options (set by the host from `IMISON_USER` and `IMISON_PASSWORD`) and are never stored in the database. `%Imison.Config{}` derives `Inspect` without `:password`, so the password never appears when the config is printed (it is the capture worker's state, the supervisor's init argument and the Registry value, all of which can show up in crash reports).

Sign in, stay signed in, sign out (AUTH-02). `imison_dashboard` also mounts `Imison.Web.SessionController` (`lib/imison/web/session_controller.ex`, a plain Phoenix controller, since only a plain request can write the session cookie): `GET <path>/login` (`new`), `POST <path>/login` (`create`) and `POST <path>/logout` (`delete`), each with route `private: %{imison_name: name, imison_dashboard_path: full_path}`, which names the instance whose login is checked. The controller renders `Imison.Web.SessionHTML.new/1` (the `docs/design/login.html` form, posting the host's CSRF token, over a deterministic mosaic of 1,500 heat cells) inside `Imison.Web.Layouts.root/1`, so the login page loads the same digested assets. `create` checks `Auth.valid_credentials?/3`; on success `Auth.sign_in/2` renews the session and puts `"imison_auth"`, an HMAC-SHA256 of `username <> <<0>> <> password` keyed with an HMAC of the endpoint's `secret_key_base`, then redirects to the dashboard root; on failure it re-renders with a 401 and "Wrong username or password.", setting nothing. `delete` calls `Auth.sign_out/1` (deletes only that key, leaving the host's session alone) and redirects to the login page. `Auth.on_mount(:require_sign_in, …)` recomputes the value from the instance's current config and compares it with the session's using `Plug.Crypto.secure_compare/2` on both the static and connected mount, redirecting to `<path>/login` when it doesn't match: no server-side state, valid on every node sharing `secret_key_base`, and a password change invalidates every session. Sign out ends only that browser's session: the value depends only on the credentials and `secret_key_base`, so a copied cookie stays valid until the password changes. `Imison.Web.Paths` (`lib/imison/web/paths.ex`) builds the login and logout URLs for `Auth`, `Layouts` and the controller, so none of them depends on another for a path. The Sign out button is a plain form posting to `<path>/logout` with the CSRF token LiveView loads from the session.

Install task (INS-01). `mix imison.install` (`lib/mix/tasks/imison.install.ex`), modelled on `mix oban.install`: `Mix.Tasks.Imison.Install` is an `Igniter.Mix.Task` (group `:imison`, so `mix igniter.install imison` runs it), defined only when `Igniter` is loaded; otherwise a plain `Mix.Task` of the same name raises that Igniter is required (INS-04 replaces it with the manual steps). The texts live in `Mix.Tasks.Imison.Install.Docs`, outside the `if`. `igniter/1` picks the repo (`Igniter.Libs.Ecto.select_repo/1`; none adds an issue and writes nothing), then: `:imison` in `.formatter.exs` `import_deps` (first, so the route it writes is formatted without parentheses); `Igniter.Project.Config.configure_new/6` per key in `config.exs` (`repo`; `pubsub`, read from the `pubsub_server` of the app's `config :app, _, pubsub_server: …` in `config.exs`, else `<App>.PubSub`; `mailer` when `<App>.Mailer` exists), `dev.exs` (`username: "admin"`, a 24-character `Base.url_encode64` of 18 `:crypto.strong_rand_bytes`) and `test.exs` (`enabled: false`, `username`/`password` `"test"`); `configure_runtime_env/6` with a keep-existing updater for the `:prod` block of `runtime.exs`; `Igniter.Project.Application.add_new_child/3` after the repo and `Phoenix.PubSub`; `Igniter.Libs.Ecto.gen_migration/4` `add_imison` with `on_exists: :skip`; and, when the router has no `imison_dashboard` call, `import Imison.Web.Router` after its `use …, :router` (unless present) and `Igniter.Libs.Phoenix.add_scope/4` `scope "/"` at the end of the router. Every step is skipped when already there, so a second run changes nothing. Tests (`test/mix/tasks/imison.install_test.exs`) run it on `Igniter.Test.phx_test_project/1`, which needs `phx_new` (a test-only dependency).

The dashboard stylesheet and its bundled fonts are in `priv/static/`, with mockups in `docs/design/`. Tooling is in place: Styler (`.formatter.exs`, which also imports the `ecto`, `ecto_sql` and `phoenix` formatter config and exports `imison_dashboard` as a local without parentheses, so a host that imports Imison's formatter config writes `imison_dashboard "/errors"`), Credo with ExSlop (`.credo.exs`).

`.gitignore` excludes `dev/`, where each maintainer keeps a local Phoenix host app for development; it is not in the repo (see the README).

## Stack

Elixir 1.20. Runtime dependencies: `ecto_sql`, `postgrex`, `telemetry`, `phoenix_live_view` (which brings `phoenix`, `phoenix_html` and `plug`). Optional: `swoosh` (the email channel compiles only when the host has it; required for Imison's own tests) and `igniter` (`mix imison.install` needs it in the host). Test only: `lazy_html` (LiveView's test HTML parser), `phx_new` (the Phoenix project the installer's tests run on). Planned: `jason`. ## Data

All tables are owned by Imison, live in the host's database (schema `public` unless `prefix` says otherwise) and are prefixed `imison_`. Version 1 creates them; ids are `bigserial`, timestamps `utc_datetime_usec` (except `imison_hourly_counts.hour`, `utc_datetime`), status-like values text.

- `imison_errors`: one row per fingerprint (unique index on `fingerprint`; index on `(status, last_seen_at)` for the error list), with status, mute flag, first and last seen, occurrence count and `regressed_at` (nullable: when a resolved error last came back; set in the same `ON CONFLICT` update that flips `resolved` to `unresolved`)
- `imison_occurrences`: stack trace and context (jsonb: `request`, `metadata`, and `runtime.node`, the node that captured it), release, time; `error_id` cascades on delete; indexed on `(error_id, occurred_at)`
- `imison_hourly_counts`: count per error per hour; unique `(error_id, hour)`; `error_id` cascades on delete
- `imison_channels`: notification channel type (unique: one row per channel type), enabled flag, config (jsonb; the email channel's is `{"recipients": [...]}`)
- `imison_rules`: notification trigger (unique) and enabled flag; a trigger without a row is enabled for `new` and `regression` only
- `imison_deliveries`: sent notifications; `channel_id` and `error_id` (nullable, digests have none) cascade on delete and are indexed
